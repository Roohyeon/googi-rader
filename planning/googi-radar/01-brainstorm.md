# 고기 레이더 — 1. 아이디어 발산
> 상태: 사용자 확인 완료 (2026-11-10)

## 출발점
- 사용자가 처음 말한 아이디어: "고기집들마다 그램(g)이 다 다르고 가격도 다 달라. 그래서 고기집 가게를 비교하고 싶어. 비교하면서 양 많이 주고(그램 많이) 가격은 낮은 곳이면 정말 좋겠지? 그렇지 않은 곳이 많으니 그걸 최소한 비교하면서 맛있는 고기집을 볼 수 있는데 서비스를 만들고 싶어."
- 다시 적은 문제:
  - 고기집을 고르는 사람은 메뉴판의 "1인분"이 가게마다 120g, 150g, 200g처럼 다르고 중량을 아예 안 적은 곳도 있어서, **같은 돈으로 실제로 얼마나 먹는지** 비교하기 어렵다.
  - 지도·리뷰 앱은 맛과 분위기 평점은 보여주지만 **100g당 가격** 같은 같은 기준의 숫자는 보여주지 않는다.
  - 원하는 결과: "가성비(100g당 가격)도 좋고 맛도 괜찮은 집"을 빠르게 찾는 것.
- 작업 폴더 확인: `googi radar` 폴더는 아직 비어 있다(`.vscode/settings.json`만 있음, 커밋 없음). 기존 코드나 자료 없음.

## 미리 짚을 점 (추론, 미확인)
- 비교하려면 **같은 부위·같은 원산지/등급**끼리 비교해야 공정하다. 국내산 한돈 삼겹살 100g과 수입 삼겹살 100g을 같은 줄에 놓으면 오해가 생긴다.
- **메뉴판에 적힌 중량**과 **실제로 나오는 중량**이 다를 수 있다. 사용자가 말한 "양 많이 주는 곳"은 어느 쪽인지에 따라 서비스가 달라진다.
- 가장 큰 숙제는 화면이 아니라 **데이터**다. 부위별 중량과 가격을 누가 모으고, 가격이 바뀌면 누가 고치는가.

## 해결 방향 후보

### A. 100g당 가격 순위 지도 (처음 아이디어)
- 한 줄 설명: 지역별 고기집의 부위·중량·가격을 모아 100g당 가격으로 환산하고, 맛 평점과 함께 지도와 목록에서 정렬·비교한다.
- 숨은 가정:
  1. 충분한 수의 가게에서 부위별 중량·가격 데이터를 정확하게 모을 수 있다.
  2. 사람들이 고기집을 고를 때 100g당 가격을 실제 기준으로 쓴다(맛·거리·분위기보다 덜 중요하지 않다).
  3. 맛 평점은 기존 리뷰(지도 앱 평점 등)를 가져오거나 자체 평가로 대체할 수 있다.
- 장점: 처음 그린 그림 그대로, 사용자에게 가치가 바로 보인다.
- 위험: 데이터 수집과 최신 유지 비용이 크고, 데이터가 적으면 빈 지도가 된다. 외부 평점을 가져오는 것은 약관 문제가 있을 수 있다.
- 가장 빨리 검증하는 방법: 한 동네 고기집 10~20곳의 메뉴 정보를 손으로 모아 보고, 중량이 공개된 곳이 몇 %인지 센다.

### B. 메뉴판 사진 → 100g당 가격 계산기 (사용자가 데이터를 모으는 구조)
- 한 줄 설명: 가게에서 메뉴판을 찍으면 부위·중량·가격을 읽어 100g당 가격을 바로 보여주고, 그 결과가 가게 데이터로 쌓인다.
- 숨은 가정:
  1. 사람들이 가게에서 메뉴판을 찍어 올릴 동기가 있다(나에게 바로 쓸모가 있으니까).
  2. 메뉴판 사진에서 중량과 가격을 꽤 정확하게 읽어낼 수 있다(손글씨, 벽 메뉴판).
- 장점: 데이터 문제를 사용자 행동으로 풀고, 처음부터 혼자서도 쓸모가 있다(계산기).
- 위험: 이미 가게에 들어간 뒤에야 쓰게 되어 "가게 고르기"에는 늦을 수 있다. 사진 인식 품질.
- 가장 빨리 검증하는 방법: 실제 메뉴판 사진 20장을 모아 사람이 직접 계산해 보고, 중량이 적힌 비율과 읽기 어려운 비율을 본다.

### C. 가장 작게: 한 동네 "고기집 가성비 표"를 직접 만들어 공유
- 한 줄 설명: 서비스 개발 없이 한 지역(예: 학교 근처) 고기집을 직접 조사해 구글 시트·노션·인스타 카드로 100g당 가격 순위를 공개한다.
- 숨은 가정:
  1. 한 동네만으로도 보는 사람이 생긴다.
  2. 직접 조사(방문·전화·메뉴 사진)가 감당할 만한 양이다.
- 장점: 비용 거의 0, 1~2주 안에 "사람들이 이걸 원하나"를 확인.
- 위험: 서비스로 키우기 전까지 확장성 없음.
- 가장 빨리 검증하는 방법: 표를 만들어 커뮤니티나 단톡방에 올리고 반응(조회, 저장, 공유)을 본다.

### D. "표시 중량 vs 실제 중량" 검증 (정직한 가게 찾기)
- 한 줄 설명: 메뉴판 숫자가 아니라 실제로 나온 양을 사용자 제보(접시 사진, 휴대용 저울 측정)로 모아 "표시대로 주는 가게"를 가려낸다.
- 숨은 가정:
  1. 표시 중량보다 적게 주는 가게가 실제로 많고, 사람들이 그걸 신경 쓴다.
  2. 실측 제보를 믿을 만하게 모을 수 있다(사진만으로 중량 추정은 어려움).
- 장점: 다른 서비스에 없는 차별점, 사용자가 말한 "그렇지 않은 곳이 많으니"에 정면으로 답한다.
- 위험: 측정이 어렵고 분쟁(가게의 반발, 허위 제보) 가능성.
- 가장 빨리 검증하는 방법: 직접 몇 곳에서 저울로 재 보고 차이가 실제로 있는지 확인.

### E. 가게가 직접 등록하는 "가성비 인증" 채널
- 한 줄 설명: 사장님이 부위·중량·가격을 직접 등록하면 100g당 가격 배지와 함께 노출되는 홍보 채널. 사용자는 검증된 데이터만 본다.
- 숨은 가정:
  1. 가성비에 자신 있는 가게가 직접 등록할 동기가 있다.
  2. 등록된 정보가 사실인지 확인할 방법이 있다.
- 장점: 데이터 최신 유지 부담을 가게가 진다. 나중에 수익 모델(광고·제휴)과 연결 가능.
- 위험: 초기에 가게를 모으기 어렵고(닭이 먼저냐 달걀이 먼저냐), 가성비 나쁜 가게는 등록하지 않아 비교가 안 된다.
- 가장 빨리 검증하는 방법: 동네 고기집 사장님 5명에게 등록 의향을 물어본다.

## 비교
| 방향 | 만드는 비용 | 핵심 가정의 위험도 | 검증 속도 | 데이터를 누가 모으나 |
|---|---|---|---|---|
| A. 100g당 가격 지도 | 높음 | 높음 (데이터 확보) | 보통 | 운영자 |
| B. 메뉴판 사진 계산기 | 중간 | 중간 (참여 동기, 인식 품질) | 빠름 | 사용자 |
| C. 동네 가성비 표 | 매우 낮음 | 낮음 | 매우 빠름 | 운영자(손으로) |
| D. 실제 중량 검증 | 중간 | 높음 (측정 신뢰도) | 보통 | 사용자 |
| E. 가게 직접 등록 | 중간 | 높음 (가게 참여) | 느림 | 가게 |

## 의견 (Claude 추천, 확정 아님)
- **C로 먼저 수요를 확인하고 A+B로 가는 순서**가 가장 덜 위험하다고 본다. A의 가치는 분명하지만 데이터가 비면 의미가 없으므로, B의 "사진 한 장으로 계산" 기능을 데이터 수집 수단으로 같이 두는 편이 좋다.
- D는 강한 차별점이지만 측정 문제가 풀리기 전에는 보조 기능(제보)으로 두는 편이 안전하다.

## 가장 위험한 가정 (사용자 의견 대기)
- **"부위별 중량·가격 데이터를 충분히, 그리고 최신으로 모을 수 있다."** 이게 무너지면 A·E는 빈 지도가 된다. 누가 데이터를 모을 것인가(운영자 직접 / 사용자 사진 / 가게 등록)가 방향을 가른다.

## 사용자 답변과 확인한 사실 (2026-11-10)
- "양 많이 주는 곳"의 기준 (사용자 답): 실제 측정이 아니라 **메뉴에 적힌 중량·가격 데이터를 비교해 그나마 그램 수가 많은(100g당 가격이 낮은) 곳**. → D(실측 검증)는 핵심이 아님.
- 사용자 제안: 카카오 지도 API로 고기집만 골라 메뉴를 확인하면 되지 않나?
- 확인한 사실 (Kakao Developers 로컬 API 개발 가이드, 키워드/카테고리 장소 검색):
  - 응답 필드: id, place_name, category_name, category_group_code, category_group_name, phone, address_name, road_address_name, x, y, place_url, distance. **메뉴·가격·중량 필드는 없음.**
  - 고기집 전용 카테고리 코드는 없음. `FD6`(음식점) + 키워드 "고기집", "삼겹살" 등으로 걸러야 함. category_name은 "대분류 > 중분류 > ..." 문자열.
  - 한 번 검색에 노출되는 결과는 최대 45개(size 최대 15 × 페이지). 넓은 지역은 좌표·반경을 나눠 여러 번 검색해야 함.
  - 메뉴는 place_url(카카오맵 상세 페이지)에서만 볼 수 있음. 이 페이지를 자동으로 긁어오는 것은 공식 API가 아니며 약관 위반 소지가 있음(약관 원문은 아직 확인하지 않음).
  - 결론: **카카오 API로 "고기집 목록·위치"는 해결되지만, "중량·가격"은 다른 방법(사용자 입력, 메뉴판 사진, 직접 조사)이 필요함.**

## 기존 데이터 조사 (2026-11-10, 웹 검색)
사용자 질문: 공공데이터포털 등에 가게별 100g당 가격 데이터가 이미 있지 않나?
- **가게별 100g당 가격을 모아 둔 공개 데이터나 고깃집 비교 서비스는 찾지 못함.** (검색 범위 안에서. "없다"고 단정할 수는 없음)
- **법적 표시 의무 (중요):** 2013년 식품위생법 시행규칙 개정으로 음식점의 고기 가격은 **100g당 가격으로 표시**하게 됨. 1인분 중량·가격을 함께 적는 것은 허용(예: "등심 100g 2만2000원(1인분 150g 3만3000원)"). → 원칙적으로 모든 고깃집 메뉴판에 100g당 가격이 있어야 함. 현행 조문이 그대로인지, 실제로 얼마나 지키는지는 미확인.
- **착한가격업소 데이터 (공공데이터포털, 지자체별):** 부산(메뉴별 가격 API), 서울(월 1회 CSV), 대전·계룡·용인 등. 업소명·주소·품목·가격이 있으나 **중량은 없는 것으로 보이고**(미확인), 저렴한 업소로 지정된 곳만 포함, 지역마다 형식이 다름.
- **한국소비자원 참가격 외식비:** 삼겹살 1인분을 200g으로 환산한 **지역 평균 가격**(예: 2026년 6월 서울 21,321원). 가게별 데이터는 아님. → "이 가게는 서울 평균보다 몇 % 싸다" 같은 **기준선**으로 쓸 수 있음.
- **여기고기 (축산물품질평가원 앱):** 정육점·마트 등 판매점의 100g당 소매 가격 비교. 식당 메뉴 아님.
- 범용 "그램당 가격 계산기" 앱은 여럿 있으나 고깃집 전용·가게 데이터 축적형은 아님.
- 시사점: 데이터는 메뉴판에 이미 적혀 있을 가능성이 높으나 **어디에도 모여 있지 않음**. 그래서 B(메뉴판 사진 수집)의 가치가 커짐(계산보다 "모으기"가 핵심).

## 선택한 방향
- 선택 (사용자 선택, 2026-11-10): **A + B + C + 외부 데이터 결합**
  - A: 고기집의 100g당 가격을 맛 정보와 함께 지도·목록으로 비교
  - 카카오 로컬 API: 고기집 목록·위치·상세 링크
  - B: 메뉴판 사진(또는 직접 입력)으로 부위·중량·가격 수집
  - 참가격: 지역 평균(삼겹살 200g 환산)을 기준선으로 비교
  - C: 초기에는 운영자가 한 동네를 직접 채워서 시작
- 사용자가 밝힌 이유: 따로 밝히지 않음 (Claude 제안에 동의)
- 버린 방향: D(실측 검증)는 기준이 "메뉴 표기 중량"이므로 핵심에서 제외. E(가게 직접 등록)는 이번에 선택하지 않음(제외 이유는 사용자가 말하지 않음).

## 2단계로 넘길 것
- 검증해야 할 핵심 가정:
  1. 고깃집 메뉴판에 100g당 가격 또는 1인분 중량이 실제로 적혀 있다(법적 표시 의무의 준수율).
  2. 사용자가 메뉴판 사진을 올릴 동기가 있다.
  3. 사람들이 고깃집을 고를 때 100g당 가격을 실제로 기준으로 쓴다.
- 아직 정하지 않은 것: 첫 대상 지역, 대상 부위(삼겹살만? 소고기 포함?), 비교 단위(같은 부위끼리), "맛있는 고기집" 정보를 어디서 가져올지(외부 평점 / 자체 평가), 사진 입력 방식(자동 인식 / 직접 입력), 웹·앱 여부, 수익 모델 유무
- 기능 폴더 이름: `googi-radar` (사용자 확인)
